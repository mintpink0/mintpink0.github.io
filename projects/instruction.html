02 — Game & Role게임과 제 역할

야간 경비원이 되어 태블릿의 근무수칙을 지키며 5일 동안 학교를 순찰합니다. 하루는 출근 → 회사 문자 지시 → 점검 → 몬스터 조우 → 판정 → 퇴근 · 근무일지 순서로 흐릅니다.

수칙을 어기면 보이지 않는 청각 · 조도 · 배치 축이 오르고, 오를수록 학교의 소리 · 조명 · 배치가 변합니다. 한 축이라도 끝까지 오르면 붙잡혀 그 밤을 다시 시작합니다. 수칙을 잘 지키면 신뢰가 오르는데, 신뢰가 높을수록 수칙서 글자가 바뀌는 변조, 수칙과 반대인 회사 문자(역설), 두 수칙이 부딪히는 딜레마가 늘어 숙련된 플레이어일수록 수칙 자체를 의심하게 됩니다.

03 — Architecture구조 — 규칙(Core)과 화면(Flow)

판정 로직은 Unity를 모르는 일반 C#으로, 화면에 그리는 일은 MonoBehaviour로 나누고 두 층 사이 통로를 두 개로 제한했습니다.

Flow · MonoBehaviour

판정 센서 — 공간 출입, 손전등 원뿔(15° · 8m) + 레이캐스트 가림, 응시, 자세, 달리기를 0.1초 간격으로 측정

조명 · 정전, CCTV, 조우 연출, 붙잡힘, 오디오

JudgeSignal →
NightRun.Send ← EventBus
BandChanged 등

Core · NightDuty.Core.asmdef (참조 없음)

판정 책(수칙별 판정기) · 공포 축 0–99 · 구간(그 밤엔 내려가지 않음)

공포 디렉터 · 편성(시드 난수, 같은 시드는 같은 결과) · 점검표 정산

연출은 수치를 직접 읽지 않고 「구간이 바뀌었다」 같은 이벤트(BandChanged · DirectionEmitted · Captured)만 받습니다.

  • 게임을 켜지 않고 검증. Core는 new만 하면 돌아가므로 자동 테스트와 밸런스 시뮬레이션을 에디터에서 바로 돌렸습니다. 테스트 폴더
  • 의존 방향을 컴파일 단계에서 강제. asmdef로 Core가 Flow를 참조하지 못하게 막아, 「축이 올랐으니 Core에서 바로 불을 끄자」 같은 우회를 차단했습니다.
  • 새 코드의 자리가 정해짐. 고르는 것(편성 · 디렉터), 판단하는 것(판정 · 점검), 숫자를 올리는 것(축), 그리는 것(Flow)으로 위치를 정했습니다.
다시 만든다면Core 입구(NightRun)가 정적 클래스라 테스트마다 초기화가 필요했고 플레이 세션 사이 리셋도 따로 처리했습니다. 인스턴스로 만들고 주입하는 구조를 쓰겠습니다.

04 — Working with AIAI와 일한 방식

Unity 에디터를 띄워 둔 채 Claude 데스크톱 앱(Opus 5.5)을 Unity CLI의 MCP 서버로 연결해 명령을 내렸습니다. 코드 · 씬 수정, 테스트 · 디버깅, 밤샘 QA 플레이까지 에디터 작업 대부분을 AI가 했고, 저는 무엇을 만들지, 어떤 숫자가 맞는지, 결과를 받아들일지를 정했습니다.

AI 제안을 받아들이지 않은 경우

상황AI 제안제 판단과 근거결과
조우 목격률못 본 조우는 다음 뽑기에 가산점(이월), 차단 조건 면제 — 예상 75 → 85~90%날짜마다 정해 둔 조우를 그날 보여 주는 것을 기획 의도로 우선했습니다. 「모든 연출에서 축 조건 제거 … 이월은 없어. 의도한 날짜에 무조건 목격해야 해」고정 날짜 편성으로 전환 (아래)
시야를 돌리면 조명이 깜빡임오클루전 컬링 끄기「성능에 큰 문제가 생길 가능성이 있나?」 → 「달빛을 꺼보고 한번 비교해봐」컬링 끄기는 렌더 4.4 → 5.4ms라 기각. 달빛만 끄는 안 3.5ms 채택, 실내 11곳 × 12방향 화면 차이 0

조명 문제의 측정(6° 간격으로 한 바퀴 렌더해 화면 평균 밝기 기록 — 특정 각도에서 48 → 71로 튐)과 원인 진단(오클루전 컬링이 달빛 그림자 캐스터도 시야 기준으로 걸러 냄)은 AI가 했습니다. 저는 문제를 발견하고, 두 안을 같은 조건에서 비교하게 한 뒤 골랐습니다.

AI에게 건 규칙

AI가 매 세션 읽는 프로젝트 문서(CLAUDE.md)에 규칙을 두었습니다.

  • 「재지 않은 것을 적지 마십시오」 (2026-09-21) — 문서가 반복해서 틀린 원인이 확인하지 않고 쓴 문장이었기 때문에 넣었습니다.
  • 구현이 끝나면 개정 기록을 남기고, 바뀐 옛 값은 「되살리지 마십시오」 목록에 올림 — 새 세션이 옛 값을 다시 가져오지 않게 하려는 장치로, 115곳에 기록이 쌓였습니다.
  • 설계 문서와 코드 값이 어긋나면 실패하는 테스트(DesignDriftTests)를 두었습니다.
  • git 명령은 AI가 실행하지 않음 — 커밋 · 병합 · LFS 잠금은 제가 직접 했습니다.

에이전트를 나눠 쓰는 방식

한 세션에 모든 일을 맡기지 않고, 조사 · 회의 · QA · 검토를 맡을 에이전트를 따로 두었습니다. 에이전트는 결과를 정리해 보고하고, 채택과 기각은 제가 정했습니다.

방식이렇게 시켰습니다결과
조사 → 회의 → 보고여러 에이전트에게 분야별 자료를 조사하게 한 뒤 회의 · 검토를 거쳐 보고하게 함. 「긴장감 컨트롤러도 다시 한번 전문가 에이전트들과 회의」공포 분위기를 만드는 방법을 여러 자료에서 종합한 선택지로 받아 고름. 회의 결과는 제안서 문서로 남김 (예: 「야간근무 3차 회의 — 경비원다운 [근무 지시]」)

05 — Troubleshooting 1조우 편성 — 확률에서 고정 날짜로

미숙한 플레이어가 조우를 다 못 보는 문제

103–104차 · 시뮬레이션
상황
감각 수치와 확률로 조우를 뽑던 편성에서, 미숙한 플레이어는 늦은 슬롯이 꺼져 조우 13종을 다 보지 못했고 붙잡힘 원인도 배치 축에 쏠렸습니다.
측정
실제 편성 코드를 그대로 쓰는 시뮬레이터로 숙련도별 가상 플레이어 400판을 돌렸습니다. 미숙 플레이어가 13종을 모두 본 회차는 21%였습니다. Core가 Unity와 분리돼 있어 가능했습니다.
조정
날짜 흐름을 바꿔 미숙 21% → 54%. 시체 낙하를 2일차로 고정하고 강도를 낮춰 보통 78% → 100%, 미숙 55% → 75%.
다시 재기
「편성됐는가」가 아니라 「실제로 실행됐는가」로 다시 세자 미숙은 33%(편성 기준 76%)였습니다. 시뮬레이션에서는 위험한 분위기 때문에 늦은 조우가 꺼졌고, 직접 플레이에서는 조우를 보기 전에 퇴근 트리거가 켜지거나 플레이어가 움직이지 않는 사이 시간이 흘러 밤이 끝났습니다.
판단
AI의 이월 보정안 대신, 축 조건을 없애고 날마다 정해진 조우를 보여 주는 고정 날짜 편성으로 바꿨습니다. 03:30에 남은 조우가 있으면 시계를 붙들어, 그날의 조우가 끝나기 전에는 다음 날로 넘어가지 않게 했습니다. 이후 「너무 고정이니 매력이 떨어진 느낌」이 들어 AI 변주안 중 같은 날 순서 섞기 · 날마다 빈 칸 · 위반 후속을 채택했고, 후속은 버그 위험 때문에 두 번에 걸쳐 다시 뺐습니다(「후속 개념은 없애줘. 버그가 너무 많을 것 같네」).
검증

한계

06 — Troubleshooting 2빌드에서만 난 문제

세 건 모두 에디터에서는 보이지 않았습니다. 추측으로 고치지 않고 릴리스 빌드를 떠서 값을 쟀습니다.

시점이 가끔 크게 휙 꺾임

102 → 104차 · 직접 발견
발견
빌드를 직접 플레이하다 발견했습니다. 「마우스에 뭔가 뚝 뚝 끊기면서 확 꺾이는 현상이 조금씩 있어」
원인
1인칭 조작 코드(김진선 님 담당)는 회전 = 마우스 이동 × Time.deltaTime × 감도였습니다. 마우스 이동(Input.GetAxis)은 이미 그 프레임 동안 쌓인 양이라 프레임 시간이 두 번 곱해져, 끊긴 프레임의 회전은 프레임 시간의 제곱으로 커졌습니다. 빌드는 프레임 제한이 없어(수직 동기 0) 보통 프레임이 수 ms였고, 20–50ms 끊김도 평소의 몇 배가 됐습니다.
1차 시도
프레임 시간 상한(1/20초)을 걸었지만 에디터 기준 값이라 빌드의 작은 끊김을 잡지 못했습니다.
해결
LookSpikeGuard가 조작 코드보다 먼저(실행 순서 −200) 돌며, 최근 「보통 프레임 시간」을 느린 평균으로 따라가고 이번 프레임 감도에 보통 ÷ 이번을 곱했다가 LateUpdate에서 되돌립니다. 빌드는 vSyncCount = 0, targetFrameRate = 144로 고정했습니다. 모의 실험(평소 5ms에 30ms 끊김 한 번)에서 회전량 90 → 15. 
// 보통 프레임엔 8%, 1.5배 넘는 끊김엔 2%만 따라간다 — 한 번의 끊김에 기준이 흔들리지 않게
public static float ScaleFor(float deltaTime, float steady)
{
    if (deltaTime <= 0f || steady <= 0f) return 1f;
    return Mathf.Clamp(steady / deltaTime, MinScale, MaxScale);
}
감도 × (보통 dt ÷ 이번 dt) → 끊긴 프레임은 쌓인 마우스 이동만큼만 회전LookSpikeGuard.cs
한계
이 보정은 끊긴 프레임만 상쇄합니다. 프레임이 고르면 배수가 1이라 원래 식이 그대로 남아, 같은 손 움직임에도 초당 회전량이 프레임 시간에 비례합니다. 60fps로 꾸준히 도는 PC는 144fps보다 약 2.4배 더 돕니다. 144fps 고정이 이 차이를 가렸습니다. 근본 원인은 마우스 값에 deltaTime을 곱하는 한 줄인데, 마감 직전이라 팀원 코드를 고치지 않는다는 경계를 지켰습니다. 다시 한다면 담당자와 합의해 그 곱을 빼고 보정 컴포넌트는 지우겠습니다.

발광이 꺼지고 머리카락 카드가 네모로 보임

빌드 전 점검 · AI 발견
발견
빌드 전에 「다른 문제는 없을지」 점검을 맡겼고, AI가 찾아냈습니다. 제가 먼저 본 문제는 아닙니다.
원인
빌드는 빌드에 포함된 재질이 쓰는 키워드 조합만 셰이더 변형으로 넣습니다. 실행 중 코드로 켜는 조합(URP Lit _EMISSION, Unlit 알파 테스트 · 반투명)이 빠졌습니다.
해결
에디터 도구 ShaderKeepBuilder가 빌드 재질을 훑어 빠진 조합마다 키워드를 켠 보존 재질을 생성합니다. 빠져 있던 조합 21개(Lit 18 · Unlit 3)를 복구했고, 조합이 다시 빠지면 실패하는 테스트를 추가했습니다. ShaderKeepBuilder.cs

릴리스 빌드에서만 소년이 머리를 박지 않음

104차 · 직접 발견
발견
릴리스 빌드를 직접 플레이하다 발견했습니다. 소리는 나는데 동작이 없었습니다.
원인
애니메이터가 없는 대역 모델에 AnimationClip.SampleAnimation으로 클립을 재생했는데, 레거시가 아닌 클립은 빌드에서 Animator 없이 샘플링되지 않았습니다.
해결
임시 씬으로 릴리스 빌드를 떠 머리 이동량을 실측했습니다(0m → 0.29m, 에디터와 같게 복구). 클립을 레거시로 전환(GUID · 곡선 유지)하고 대역 생성 도구도 고쳤으며 회귀 테스트를 추가했습니다.

「에디터에서 된다」는 「빌드에서 된다」가 아니었습니다. 플랫폼 차이가 의심되면 작은 빌드로 재현하고 숫자로 확인합니다.
